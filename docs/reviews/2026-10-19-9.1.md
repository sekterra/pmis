## 확인한 것
- 보고서 체크리스트 17항목이 지시서와 맞고, 근거 테스트 이름이 diff 에 실제로 있다. 단위 62, 통합 36 통과, 실패 0.
- 테넌트 DDL 변경 없음(db/migration 미수정). `it-` 아닌 `pmis.tenant` 행 수 불변 확인 테스트 있음.
- CompanyService: 코드 불변, 사업자번호 부분 유니크(사용 중만), 상위 순환(자기 자신, 상위 체인 추적), 삭제 거절 4종(하위 회사, 사용 중 부서, 현재 소속, 마지막 OWN), 복구 시 상위·사업자번호 재검사.
- DeptService: 이동 시 `dept_path`/`level_no` 하위 일괄 갱신(경로 접두사 정확 일치 또는 `접두사/%`), 이동 후 `entityManager.clear()` 로 재조회, RENAME/MOVE/CLOSE/REOPEN 이력, 순환·회사 불일치 검사, 트리는 `asOfDate` 가 있으면 사용 여부 무시.
- PersonService: 목록의 주 소속 요약을 IN 쿼리 한 번으로 조회, 키워드가 현재 소속의 사번까지 검색, 삭제 거절 2종(소속, 계정).
- PersonAssignmentService: 부서-회사 일치, 현재 소속 중복, 사번 유니크(V5), 첫 소속 자동 주소속, 새 주소속 시 기존 강등, 종료 시 자동 승격 없음, 복구는 같은 검증을 다시 통과.
- 감사자는 테넌트 토큰의 `sub` 만 읽고 플랫폼 토큰·무인증은 비어 있다.

## 작은 보완 (9.2 지시서 A절)
1. 부서 수정에서 상위가 바뀌지 않아도 `DEPT.PARENT_INACTIVE` 를 검사해, 현재 상위가 폐지된 부서의 이름만 고치는 요청이 막힌다.
2. 소속 종료 API 가 이미 종료된 소속이나 논리 삭제된 소속에도 다시 적용된다(종료일·상태 덮어씀).
3. 부서 트리 조립이 행마다 전체 목록을 훑는다(O(n²)). 지금 규모에서는 문제 없지만 정리한다.

## 사용자 결정으로 확정된 가정
- 회사 코드 형식 `^[A-Z0-9_-]{1,50}$` (ERD 에는 길이 50, 유니크만 있음).
- 국가 오류는 `COMMON.VALIDATION_FAILED` + `fieldErrors(nationCode)`.
- 목록 `useYn` 생략은 사용 중지 포함, 부서 트리만 오늘 기준 사용 중.
- 복구 권한은 UPDATE.

## 한계(문서에 있음)
- 과거 시점 조직도 재구성 없음. 주 소속 조회 횟수는 목 검증이며 SQL 통계는 없음.
- 논리 삭제한 회사·부서 코드는 다시 쓸 수 없다.
- 9.1 은 공유 DB 에 마이그레이션을 적용하지 않았다.
