# 9.5단계 검토 (2026-10-22)

대상: `docs/reports/9.5.md`, `9.5.diff` (시작 커밋 241c31e), 핵심 코드 `FileCleanupScheduler`, `FileCleanupSchedulingConfig`, `RollbackFileCleanup`, `LikeEscape`, `StoredFile.markPurged`, 설정 파일.

## 결론

승인. 9.4 검토의 보완 5건과 정리 스케줄러가 지시서대로 반영되었다. 단위 86건, 통합 47건이 통과했다.

## 확인된 좋은 점

- 스케줄러 빈과 `@EnableScheduling` 이 모두 `mdm.file.cleanup.enabled=true` 일 때만 생긴다. 기본과 dev 는 꺼짐이다.
- 테넌트마다 `TenantContext.beginRequest()` / `setSchema` / `finally clear()` 를 쓰고, 한 테넌트의 예외가 다른 테넌트를 막지 않는다. 로그에는 테넌트 코드와 예외 종류만 남고 경로나 메시지는 없다.
- 동시 실행은 `AtomicBoolean` 으로 막는다. 단일 인스턴스 전제를 문서에 적었다.
- `LikeEscape` 로 검색어 LIKE 를 15개 서비스에서 공통 처리했다. 사용처 목록을 보고서에 남겼다.
- 롤백 시 디스크 파일 삭제는 `afterCompletion(ROLLED_BACK)` 훅으로 구현했다.
- 통합 테스트가 공유 DB 의 다른 테넌트를 건드리지 않도록 `runOnce(목록)` 을 쓴다.

## 다음 단계로 넘기는 항목

1. **`DeptService.relocate` 의 `dept_path LIKE`**: 보고서는 "경로 접두사라 그대로 둠"이라고만 적었다. `dept_path` 가 부서 PK 숫자로만 만들어지면 `_` 문제가 없지만, 부서 코드가 섞이면 9.3 메뉴와 같은 오류가 난다. 경로 구성 방식을 확인해 코드에 근거를 주석으로 남기거나, 코드가 섞여 있으면 `left` 비교로 바꾼다.
2. **시스템 감사 계정**: 스케줄러 실행 시 감사 컬럼(`update_user_pk`)이 null 이다. 현재 컬럼이 null 허용이라 동작은 문제없다. 운영 감사 요구가 생기면 테넌트 시드에 시스템 사용자를 추가한다. 지금은 보류.
3. **스케줄러 시간 예외**: `scheduled()` 에서 `journal.listTenants()` 가 실패하면 예외가 스프링 스케줄러 로그로만 남는다. 현재 수준에서 허용한다.

## 질문 답변

- 시스템 `user_pk` 없음 → 위 2번대로 null 유지, DDL 추가 없음.
