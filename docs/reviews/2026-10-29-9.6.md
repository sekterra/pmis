# 9.6단계 검토 (2026-10-29)

대상: `docs/reports/9.6.md`, `9.6.diff` (시작 커밋 58b5de6, 구현 커밋 3566243), 핵심 코드 `DeptService`, `DeptHistoryResponse`, `S03_code.sql`.

## 결론

승인. 단위 86건, 통합 50건이 통과했고 `pmis.tenant` 실제 행은 테스트 전후 같았다.

## 확인

- **부서 경로**: `dept_path` 는 `/` 와 숫자 PK 로만 만들어지고 이동 UPDATE 의 접두사는 `기존경로 + "/%"` 다. `/1/` 과 `/10/` 이 섞이지 않는다. 이스케이프가 필요 없는 이유를 코드 주석과 문서에 남겼다. PK 1·10·100 회귀 테스트가 있다.
- **이력 상위 부서 이름**: `beforeParentDeptName`, `afterParentDeptName` 이 추가되었고 페이지의 PK 를 `findAllById` 한 번으로 조회한다. 이력 1건과 2건의 prepare statement 수가 같음을 테스트로 확인했다. 값은 부서의 현재 `dept_name` 이다.
- **직위·직책 시드**: `INSERT … WHERE NOT EXISTS` 라 기존 이름·정렬을 덮지 않는다. 이름 번역은 기존 시드와 같은 `common_code_lang` 에 넣었다(지시서가 말한 `i18n_entity_text` 와 달랐지만 기존 방식이 옳다). 새 테넌트에서 소속에 `MANAGER` 직위를 저장하면 통과한다.
- **권한 현황 표**: 시드는 바꾸지 않았다. 아래 "결정" 참고.

## 알아둘 점

1. **이미 만든 테넌트에는 새 시드가 자동으로 들어가지 않는다.** 시드 실행은 새 테넌트 생성과 테넌트 업그레이드(`TenantUpgradeService.migrate`) 때 일어난다. 개발용으로 이미 만든 테넌트의 직위·직책 선택이 비어 있으면 업그레이드를 한 번 실행해야 한다. 업그레이드를 실행하는 방법(API 또는 명령)은 다음 백엔드 단계에서 문서에 정리한다.
2. 프런트 부서 화면은 아직 상위 부서 PK 만 보여 준다. 이름 필드를 쓰도록 바꾸는 작은 작업을 프런트 다음 단계에 넣는다.

## 결정: 일반 사용자 기본 권한

현황: `MANAGER` 는 조직·팀·파일에 READ/CREATE/UPDATE/EXPORT, `USER` 는 조직·팀·파일 READ, 공통코드·다국어는 READ. `USER`·`ROLE`·`PERMISSION`·`MENU`·`FILE_STORAGE` 는 `TENANT_ADMIN` 에만 있다. 이 기본값을 유지한다. 새로운 권한이 필요한 역할은 F10 역할 화면에서 만든다. DELETE 는 `TENANT_ADMIN` 만 갖는 현재 정책을 유지한다.
