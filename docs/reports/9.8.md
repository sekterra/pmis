## c. 핵심 코드

플랫폼 `POST /api/platform/v1/tenants/{tenantCode}/support-access`가 티켓을 만든다. `dev`에서는 `http://localhost:8000/support-access?tenant={코드}#ticket=` 형태다. 그 외에는 대표이면서 검증됐고 사용 중인 도메인이 있어야 한다.

교환은 `POST /api/mdm/v1/auth/support-access/exchange`다. 헤더 `X-MDM-Request: 1`이 없으면 `AUTH.CSRF`다. 조건부 UPDATE로 `ISSUED`를 `ACTIVE`로 바꾸고, 시스템 사용자 `$platform-support`를 `sub`로 하는 테넌트 JWT에 `sup`, `act`를 넣는다. 매 요청은 같은 테넌트, `ACTIVE`, 만료 전, 운영자 활성인지를 본다.

쓰기 요청은 처리 전에 `pmis.tenant_support_access_action`에 별도 트랜잭션으로 넣고, 끝나면 상태 코드를 갱신한다. 종료 API는 기록하지 않는다. 넣기에 실패하면 본 처리를 하지 않는다.

`GET /api/mdm/v1/auth/me`의 `support`는 일반 토큰에서 null이다. 지원 토큰이면 접속 번호, 운영자 로그인, 만료 시각이고 표시 이름은 `플랫폼 지원 ({운영자 로그인 ID})`다.

## e. 가정, 질문, 알려진 한계

- 상태 컬럼은 기존 코드 컬럼과 같이 `status_code`다. 설계문의 `status`와 다르다. `auth-design.md` 구현 차이에 적었다.
- 메뉴 그룹 `ACCESS`는 시드에 없다. `SUPPORT_ACCESS`는 `SYSTEM` 아래 정렬 62다. READ만 `TENANT_ADMIN`에 준다.
- 운영자를 끄는 API가 없다. 교환 시 비활성이면 티켓을 소모하지 않고 `AUTH.SUPPORT_TICKET_INVALID`다. 이미 연 세션의 다음 요청에서 `REVOKED` / `OPERATOR_DISABLED`로 두고 `AUTH.SUPPORT_ENDED`다.
- 기간 필터는 발급 시각이다. 조회에서 만료된 `ACTIVE`는 응답만 `EXPIRED`로 보여주고, 행을 고치는 것은 그 토큰의 다음 요청이다.
- 60초 캐시는 두지 않았다. 비활성화 API가 없어 캐시를 바로 지울 곳이 없다.
- `$platform-support`는 시드 SQL로만 만든다. 사용자 등록 정규식은 `$`를 거절한다. 그 아이디의 실패 로그인은 실패 횟수를 올리지 않아 계정이 잠기지 않는다.
- 사람 선택 목록은 사람 행을 보여 준다. 시스템 계정은 사람이 없다. 사용자 목록·검색·역할 보유 수·마지막 관리자 수에서는 로그인 아이디로 뺀다.
- 질문: 메뉴를 `SYSTEM`에 둔 것과, 운영자 비활성화 API 없이 요청마다 확인하는 것을 확인해 달라. 지시에서 벗어난 점: 설계 본문은 고치지 않고 구현 차이만 붙였다. ERD는 마이그레이션 테스트가 테이블 목록을 맞추므로 두 엔티티를 추가했다.
